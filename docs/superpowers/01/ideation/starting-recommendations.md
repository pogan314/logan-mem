# Starting recommendations

- These are opinions to argue with when brainstorming starts. None is a decision.
- Ordered by how strongly I hold them. The first three are the ones I would fight for.

## 1. Build the loop before anything else

- Version 01's first milestone is one thing: **a session happens → memories get written automatically → the next session sees them.** Nothing else ships until the owner has looked at a week of those memories and said "these are useful".
- That loop is small. A Stop hook that writes lessons, a folder of markdown files, a SessionStart hook that injects the relevant ones, one search tool. The old system had all the parts and never closed the loop.
- Measure it by hand: once a week the owner reads the new memories for five minutes and marks each useful / not. That number is the only success metric until it is consistently good.

## 2. Put a hard budget on version 01 and make it a rule, not a wish

- Suggested: a source-line ceiling (the second-opinion analysis proposed ~4,000 lines; the old build was 33,945), a cap on CLI commands, and exactly one install surface.
- Write the budget into `CLAUDE.md` as a constraint agents must check before adding code. "Simplify" as an adjective produced 34k lines last time; a number cannot be argued with.
- No spec document before the loop works. A one-page brainstorm, then code. The old build wrote 18k lines of plans first and agents built all of it.

## 3. Human review is a flag, never a gate

- Every memory is live the moment it is written. A `human_verified: true/false` field (or similar) records whether the owner has looked at it. Agents see both kinds; verified ones may carry more weight when two memories conflict.
- The only place a human gate belongs is the **separate** step of turning a memory into a harness component (a skill, hook, rule, or agent). That is a different system and should be designed as one, later.

## 4. Use the hook types the old system ignored

- Claude Code has `prompt` and `agent` hook types (verified against the live docs 2026-08-21 — see `docs/wiki/claude-code-harness-facts.md`). An `agent` hook on `Stop` can read the session and write lessons with tool access. The old system only used `command` hooks, which cannot run a model, so it had no cheap way to reflect.
- Caveat: the docs mark agent hooks experimental. Treat as promising; keep a command-hook fallback in mind.

## 5. Make memory kinds cheap to grow

- Kinds as a plain string with a starter list, not a locked schema enum. The old build's four kinds needed a migration to extend.
- Starter kinds worth considering (to be argued in brainstorming): decision, fact, failure, recipe, preference, convention, gotcha, environment fact, project status, open question. See `feat/memory/memory-kinds.md`.
- The failure last time was not the kinds list; it was that only one kind ever got captured. Design capture paths per kind.

## 6. Memories live with the thing they are about

- Per-repo memories go **inside the repo** (a committed folder), so `git clone` is the sharing mechanism and branches give per-branch memory for free. Per-person and cross-repo memories go in one user-level store.
- That collapses the old personal / org / shared split to two places with one rule each. Attribution is a field or the git author, not a folder.

## 7. Treat conversation history as its own layer

- `obra/episodic-memory` shows the shape: index the transcripts that already exist on disk, search them by meaning, never curate. See `docs/wiki/obra-episodic-memory.md`.
- It answers "what did we discuss about X?" It does not answer "what are my standing rules?" Those are two layers; version 01 probably wants a thin version of both, and could adopt episodic-memory as-is for the first.

## 8. Spine as a committed, annotated artifact

- A text file in the repo (one per repo, regenerated by merging not wiping), with a `note:` field per module that humans and agents can fill. Its own small subsystem. See `feat/spine/`.
- Keep it out of version 01's first milestone unless it is trivially small; it is the feature most likely to balloon.

## 9. Design the build process against drift

- Short sessions, each with one named deliverable committed to the repo. The repo holds state; the conversation does not.
- No "execute this plan" prose in any doc. Plans carry a status field and get archived when done or abandoned.
- Code comments describe the code. They never cite a spec section.
- Every doc under `docs/` has frontmatter with `status` and `updated`. An agent that reads a `stale` file and acts on it has broken a rule.

## 10. Things to drop unless a brainstorm resurrects them with a reason

- Encryption of memories. Two-person approval. Per-person folders enforced by git hooks. Member offboarding and key rotation. A doctor with 18 checks. Supermemory's benchmark suite as a gate. A glossary of 100–200 curated terms before the system has 100 memories.
